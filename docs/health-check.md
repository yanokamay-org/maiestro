# Repo health check

A **Check Health** button at the top of a repo's detail form in the Settings window runs per-repo diagnostics and shows the results in a modal, so a broken prerequisite surfaces *before* it fails mid-spawn. The backend command is `health::repo_health_check(repo) -> HealthReport` (`backend/src/health.rs`); the frontend renders it via `api.repoHealthCheck` and a `HealthModal` in `App.tsx`. Each check is a `HealthCheck { id, label, status, detail, sub, command? }` with `status ∈ {pass, fail, warn, info, skipped}`; a parent's status is the worst-case roll-up of its `sub` checks. `info` reports **no problem** — something worth knowing that needs no action — so it is deliberately left out of the roll-up ranking (a group whose only non-pass sub is informational still rolls up to `pass`), and it renders in blue rather than the warn amber. Every external command a check runs — the two `git` calls (`rev-parse --git-dir`, `remote get-url origin`) and the agent probe (`claude` or `codex`) — is logged via `log_command` at `info` (`target: "health"`, with the `repo` and the full command line; these carry no secrets), so the log shows exactly what the health check executed. The GitHub API calls it makes are logged separately at the `GitHub::send` choke point (see "Talk to GitHub directly" in `CLAUDE.md`).

The checks run sequentially and **stream** into the modal: before each check the command emits `health-check-running` (`{ repo, index, total, label }`) so the spinner names the check in flight, then `health-check` (`{ repo, index, total, check }`) when it lands, so rows appear incrementally; the command's returned `HealthReport` is the authoritative final list (reconciling any missed event). The optional `command` carries a copy-paste remediation one-liner (e.g. a `git clone https://github.com/owner/name.git <dir>` when the repo isn't checked out), rendered as a monospace `.health-command` line. That clone hint uses the **HTTPS** remote deliberately: it needs no credentials for a public repo and otherwise picks up git's existing credential helper, whereas an SSH remote would assume a GitHub SSH key the user may simply not have, making the hint a command that could never work on an HTTPS-only machine. The checks are **informational only** — they never block spawning.

**The health check modal re-probes path/tool hints on close (#147).** The natural flow around a `fail`/`warn` row is to copy its remediation command, run it in a terminal, and dismiss the modal — but the rest of the Settings window (the "Directory not found" hint under *Cloned repo dir*, the env-files hints, the Tool paths status line) only re-checks the filesystem when a field's own value changes, so a fix made this way would otherwise stay invisible until the field is retyped or the window reopened. `Settings.tsx`'s `HealthModal` `onClose` handler — reached by **Done**, the ✕ icon, Escape, and a backdrop click alike, since `OverlayDialog` funnels all four into one `onClose` — also calls `refreshProbes()`, which bumps a `probeGeneration` counter (see "Soft path validation + Finder reveal" in `docs/settings.md`) and re-fetches `toolsResolved()`. This is deliberately *not* a full settings reload: it never re-reads `settings.json`/the repo settings file and never re-seeds either form's autosave baseline, so an edit in progress survives untouched and the close itself never triggers a save. **Retry** does not refresh — the re-run in progress is itself the fresh answer.

The eight checks: **cloned repo** (`cloned_repo_dir` exists, `git rev-parse --git-dir` succeeds, *and* — as a sub-check — its `origin` remote resolves to this `owner/name`, so a checkout aimed at the wrong project is caught, not just a missing one; `remote_owner_name` parses the HTTPS/SSH/scp URL forms), **git available** (via `tools::find_tool`), **agent logged in** — for the repo's **effective agent** only (`repo_settings::effective_agent`; see "Checks are chosen per agent" below). For Claude it is **Claude logged in** with a nested **model available** sub-check (one probe, two facts: it runs a trivial `claude -p "…" --model <repo's prompt_models.claude> --output-format json --tools ""` and splits the outcome so auth and model problems are distinguishable. The parent keeps the *login* status — it is **not** rolled up from the sub — so "Claude logged in" stays green even when the model sub fails (you're logged in, you just picked a bad model). The JSON envelope is parsed *first* and is authoritative — claude exits **non-zero on an API error too** (a bad model is exit 1 with `is_error`/`api_error_status: 404`), so the exit code alone can't be trusted to mean "not logged in". Classification (`classify_claude_envelope`, a pure fn so it's unit-tested): `is_error` with `401`/`403` → *login* Fails (with a `claude login` command), model sub Skipped; `is_error` with a **null** `api_error_status` → *login* Fails too — this is the **logged-out** case (claude bails out *locally* before any HTTP request, e.g. `Not logged in · Please run /login`, so it exits 0 with an error envelope but no status; a null status means no request completed, so it must **not** be read as "auth worked, model broken"); `is_error` with any other status (notably `404`) → auth *worked*, so login Passes and the *model* sub Fails with the message; a clean reply Passes both. Only when there's **no parseable envelope** does it fall back to the exit code — a non-zero exit there is the genuine not-logged-in/couldn't-run case; a 60s timeout → `warn`), **GitHub token & permissions** (below), **session editor available** (the `code` CLI, matching what `open_vscode` actually launches; a missing CLI with VS Code.app present is a `warn`, not a `fail`), **env files exist** (each `env_files` entry resolved against `cloned_repo_dir` as the spawn copy does; missing ones are a `warn`), **terminal font installed** — whether the first concrete family in the `terminal_font_family` preference is actually on the machine, and **tool versions** (below). For Codex it is **Codex logged in**, from `check_codex`: `codex` must resolve, then `codex login status` must exit 0 (a failure suggests `codex login`; it runs first because a logged-out `codex exec` retries for a while before failing). The nested model sub does a tiny tool-less `codex exec --model <prompt_models.codex>` round trip (the same flags as drafting, `drafting::codex_exec_args`) and Fails with Codex's API error when the model is rejected; with no `prompt_models.codex` set it is `info` — drafting then uses the model configured in Codex itself, which the login check already vouches for. Detection is a **filename scan** of `~/Library/Fonts`, `/Library/Fonts` and `/System/Library/Fonts` (each one level deep, for `Supplemental`), comparing normalized names (lowercased, non-alphanumerics dropped) with the family as a *prefix* of the file name — a font file is named for the family plus its style (`JetBrainsMonoNerdFont-Regular`). That beats CoreText (a new dependency) and `system_profiler SPFontsDataType` (seconds slow) for something that sits in a health run. A missing preferred font is **`info`, never a failure**: the stack degrades to a stock face, so all that's lost is Claude Code's box/powerline glyphs. It carries a `brew install --cask …` remediation from a small **verified table** (`font_install_command`) rather than a derived name — a cask name can't be computed from a family (`JetBrainsMono Nerd Font` ships as `font-jetbrains-mono-nerd-font`), and an unknown family gets no command instead of a wrong one. The one `warn` is the genuinely broken case: *no* family in the configured stack is installed. `terminal_font_check(stack, installed)` is split from the scan so every branch is unit-tested. Across the three tool-resolving checks (**git available**, **agent logged in**, **session editor**), because a `tool_paths` override is authoritative (see `docs/tool-resolution.md`), a configured-but-missing pin is a hard **fail** naming the path (`tool_not_found_detail` → `tools::stale_override`), *not* a silent fall-through to a PATH binary — the whole point of pinning is honored. (For the editor this fail takes precedence over the VS Code.app-present `warn`.)

**Tool versions (issue #146) is a trailing group, not a per-tool sub.** The earlier checks (**git available**, **claude logged in**, **session editor available**) confirm each directly-invoked CLI *resolves*; this last group asks how old it is. mAIestro Code leans on features only newer releases have — Claude Code's `--remote-control`/`--name` launch flags, the `PostToolUseFailure` hook, `/color`; `git worktree`; VS Code's `--disable-workspace-trust` — so a stale binary can fail mid-spawn or degrade silently. It runs `<tool> --version` for the repo's agent (`claude` or `codex`), `git`, and `code` (same resolution as everything else — a `tool_paths` override is checked verbatim) and compares the first `digits(.digits)*` run on the first non-empty line of output (`parse_version`) against a **hardcoded** floor per tool (`MIN_TOOL_VERSIONS`, with the reason it exists) using component-wise comparison that treats a missing trailing component as `0` (`version_at_least`) — no `semver` dependency for three known output shapes. Below the floor is a **`warn`, never a `fail`**: an old tool might still work, and this report is informational like the rest of it; the detail names both versions and the reason, `claude` gets a `claude update` remediation and `codex` a `codex update` one (the Codex floor, 0.133.0, is the release where hooks went stable with `PermissionRequest`/`SessionEnd`), while `git` gets `brew upgrade git` only when the resolved binary actually lives under a Homebrew prefix (Apple's Xcode-stub git can't be upgraded that way) — `code` never gets one since it updates itself from its own menu. A tool `find_tool` couldn't resolve reports its version sub as `skipped` rather than repeating the failure the earlier row already surfaced at the right severity; output that ran but didn't parse (an unexpected wrapper) is `info` with a snippet of the raw text, since it isn't a known problem. Floors are a code change, not a setting — there is no `tool_paths`-style per-tool minimum override, and this is "old enough to break", not "not the newest" (no network call to check for a newer release).

**GitHub permission testing is the notable one, and it never mutates the repo.** mAIestro Code's own GitHub calls need read (repo/issues/PRs) *and* write (create/update issues, comments, assignees, create/merge PRs), so token validity alone isn't enough — but there's no side-effect-free "test this write endpoint" call. So write access is **derived, not exercised** (no throwaway issue/PR/label):
- **Token valid** — `GitHub::check_token()` does a raw (non-ETag-cached) `GET /user`, returning the login *and* the `X-OAuth-Scopes` response header. This is the only addition to `plugins/github.rs`.
- **Repo readable** — `GitHub::repo()` (`GET /repos/{owner}/{name}`), which also carries the `permissions` object.
- **Write access** — for a **classic PAT** (non-empty `X-OAuth-Scopes`) the scope list is authoritative: needs `repo` (or `public_repo` on a public repo). For a **fine-grained PAT** (empty scopes header) it reads the repo response's `permissions.push` flag. Either way the verdict ("token can read but cannot push to this repo") is inferred from what GitHub already reports.

The check uses the repo's assigned `identity_id` to pick the token (`GitHub::for_identity`); a repo with no identity assigned makes the GitHub check `skipped`. Out of scope for now: no live write probe, no `gh` CLI check, no auto-fix, and no background/periodic polling (runs only on button click).

**Checks are chosen per agent (issue #162).** Only the repo's effective agent is checked: a Codex repo doesn't run the Claude probe, doesn't list `claude` in the tool checks, and doesn't version-check it (`tool_applies` filters `MIN_TOOL_VERSIONS`), and a Claude repo doesn't mention `codex` or `agy`. `git` and `code` are always checked.

**Antigravity (issue #185)** has no login-status command. The "Antigravity logged in" row runs `agy models` instead (`check_antigravity`, classified by the pure `antigravity_checks`). It starts no model turn and spends no quota:
- **Logged out:** `agy models` exits 1 at once with "Please sign in…". That is a login Fail whose fix is running `agy` to sign in.
- **Logged in:** it lists `id\tName` per model. The login Passes, and the **model available** sub-row checks the drafting model (`prompt_models.antigravity`) against that list. `agy` has no aliases, so an id without its effort suffix (e.g. `gemini-3.8-flash` for `gemini-3.8-flash-low`) fails with the available ids.

The version floor is `agy` **1.2.10**, which fixed the headless exit codes and JSON error output that drafting relies on. The upgrade command is `agy update`. A machine with only one agent installed therefore gets a clean report for repos on that agent.
