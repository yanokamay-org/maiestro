# Repo health check

A **Check Health** button at the top of a repo's detail form in the Settings window runs per-repo diagnostics and shows the results in a modal, so a broken prerequisite surfaces *before* it fails mid-spawn. The backend command is `health::repo_health_check(repo) -> HealthReport` (`backend/src/health.rs`); the frontend renders it via `api.repoHealthCheck` and a `HealthModal` in `App.tsx`. Each check is a `HealthCheck { id, label, status, detail, sub, command? }` with `status ∈ {pass, fail, warn, info, skipped}`; a parent's status is the worst-case roll-up of its `sub` checks. `info` reports **no problem** — something worth knowing that needs no action — so it is deliberately left out of the roll-up ranking (a group whose only non-pass sub is informational still rolls up to `pass`), and it renders in blue rather than the warn amber. Every external command a check runs — the two `git` calls (`rev-parse --git-dir`, `remote get-url origin`) and the agent probe (`claude` or `codex`) — is logged via `log_command` at `info` (`target: "health"`, with the `repo` and the full command line; these carry no secrets), so the log shows exactly what the health check executed. The GitHub API calls it makes are logged separately at the `GitHub::send` choke point (see "Talk to GitHub directly" in `CLAUDE.md`).

The checks run sequentially and **stream** into the modal: before each check the command emits `health-check-running` (`{ repo, index, total, label }`) so the spinner names the check in flight, then `health-check` (`{ repo, index, total, check }`) when it lands, so rows appear incrementally; the command's returned `HealthReport` is the authoritative final list (reconciling any missed event). The optional `command` carries a copy-paste remediation one-liner (e.g. a `git clone https://github.com/owner/name.git <dir>` when the repo isn't checked out), rendered as a monospace `.health-command` line. That clone hint uses the **HTTPS** remote deliberately: it needs no credentials for a public repo and otherwise picks up git's existing credential helper, whereas an SSH remote would assume a GitHub SSH key the user may simply not have, making the hint a command that could never work on an HTTPS-only machine. The checks are **informational only** — they never block spawning.

**The health check modal re-probes path/tool hints on close.** The natural flow around a `fail`/`warn` row is to copy its remediation command, run it in a terminal, and dismiss the modal — but the rest of the Settings window (the "Directory not found" hint under *Cloned repo dir*, the env-files hints, the Tool paths status line) only re-checks the filesystem when a field's own value changes, so a fix made this way would otherwise stay invisible until the field is retyped or the window reopened. `Settings.tsx`'s `HealthModal` `onClose` handler — reached by **Done**, the ✕ icon, Escape, and a backdrop click alike, since `OverlayDialog` funnels all four into one `onClose` — also calls `refreshProbes()`, which bumps a `probeGeneration` counter (see "Soft path validation + Finder reveal" in `docs/settings.md`) and re-fetches `toolsResolved()`. This is deliberately *not* a full settings reload: it never re-reads `settings.json`/the repo settings file and never re-seeds either form's autosave baseline, so an edit in progress survives untouched and the close itself never triggers a save. **Retry** does not refresh — the re-run in progress is itself the fresh answer.

The checks (eight for a VS Code repo, seven for a Terminal.app, cmux or Windows Terminal one): **cloned repo** (`cloned_repo_dir` exists, `git rev-parse --git-dir` succeeds, *and* — as a sub-check — its `origin` remote resolves to this `owner/name`, so a checkout aimed at the wrong project is caught, not just a missing one; `remote_owner_name` parses the HTTPS/SSH/scp URL forms), **git available** (via `tools::find_tool`), **agent logged in** — for the repo's **effective agentic coding CLI** only (`repo_settings::effective_agent`; see "Checks are chosen per agentic coding CLI" below). For Claude it is **Claude logged in** with a nested **model available** sub-check (one probe, two facts: it runs a trivial `claude -p "…" --model <repo's agent_settings.claude.prompt_model> --output-format json --tools ""` and splits the outcome so auth and model problems are distinguishable. The parent keeps the *login* status — it is **not** rolled up from the sub — so "Claude logged in" stays green even when the model sub fails (you're logged in, you just picked a bad model). The JSON envelope is parsed *first* and is authoritative — claude exits **non-zero on an API error too** (a bad model is exit 1 with `is_error`/`api_error_status: 404`), so the exit code alone can't be trusted to mean "not logged in". Classification (`classify_claude_envelope`, a pure fn so it's unit-tested): `is_error` with `401`/`403` → *login* Fails (with a `claude login` command), model sub Skipped; `is_error` with a **null** `api_error_status` → *login* Fails too — this is the **logged-out** case (claude bails out *locally* before any HTTP request, e.g. `Not logged in · Please run /login`, so it exits 0 with an error envelope but no status; a null status means no request completed, so it must **not** be read as "auth worked, model broken"); `is_error` with any other status (notably `404`) → auth *worked*, so login Passes and the *model* sub Fails with the message; a clean reply Passes both. Only when there's **no parseable envelope** does it fall back to the exit code — a non-zero exit there is the genuine not-logged-in/couldn't-run case; a 60s timeout → `warn`), **GitHub token & permissions** (below), **terminal host available** — for the repo's `terminal_host` only (`repo_settings::effective_terminal_host`). For VS Code it is the `code` CLI, matching what `open_vscode` actually launches; a missing CLI with VS Code.app present is a `warn`, not a `fail`; Windows has no such fallback launch, so there a missing CLI — after probing VS Code's default install folders, see `docs/tool-resolution.md` — is a `fail`. For Terminal.app (`check_terminal_app`) it is the app at `/System/Applications/Utilities/Terminal.app` plus an **Allowed to control Terminal** sub-check (`terminal_app::automation_allowed`): a harmless Apple event, sent **only while Terminal is already running** so a health run never launches it — though it may raise macOS's Automation prompt, which is the point. Granted is a `pass`, `-1743` a `fail` naming System Settings → Privacy & Security → Automation with an `open 'x-apple.systempreferences:…Privacy_Automation'` command, and a Terminal that isn't running is `info` (the grant is asked for on the first launch); the parent rolls up the sub. It never reads or writes Terminal's profiles. For cmux (`check_cmux`) it is the `cmux` CLI (`tools::find_tool`: the one inside cmux.app, or the `tool_paths` pin, failing on a stale pin) plus an **Allowed to control cmux** sub-check (`cmux_access_check`) from `cmux --json capabilities` → `access_mode`, asked **only while cmux is running** (the CLI never starts it). `automation` and `password` are a `pass`, and the detail claims no more than the modes give: both admit only processes running as this Mac user, and in password mode the cmux CLI presents the password saved in cmux, so mAIestro Code stores none. `allowAll` ("Full open access") is a `warn`, since cmux itself calls it unsafe. An access-denied socket (the default `cmuxOnly`), a missing password and a rejected password are each a `fail` with its own message naming *cmux Settings → Automation → Socket Control Mode → Automation or Password*; a cmux that isn't running (or whose socket is off) is a `warn`. It never changes cmux's settings. For Windows Terminal (`check_windows_terminal`) it is `wt` (`tools::find_tool`: its app execution alias under `%LOCALAPPDATA%\Microsoft\WindowsApps`, or the `tool_paths` pin): resolving is a `pass`, a broken pin a `fail` naming it, and a missing `wt` a `fail` saying it is a Microsoft Store / `winget install Microsoft.WindowsTerminal` install on Windows 10 (or that its app execution alias is off) — the same message a spawn fails with. Health **never runs `wt.exe`**: any `wt` call opens a window, and `wt -v` a dialog), **env files exist** (each `env_files` entry resolved against `cloned_repo_dir` as the spawn copy does; missing ones are a `warn`), **terminal font installed** — VS Code repos only, since the preference is VS Code's terminal font (a Terminal.app session uses the user's own Terminal profile, which mAIestro Code never touches) — whether the first concrete family in the `terminal_font_family` preference is actually on the machine, and **tool versions** (below). For Codex it is **Codex logged in**, from `check_codex`: `codex` must resolve, then `codex login status` must exit 0 (a failure suggests `codex login`; it runs first because a logged-out `codex exec` retries for a while before failing). The nested model sub does a tiny tool-less `codex exec --model <agent_settings.codex.prompt_model>` round trip (the same flags as drafting, `drafting::codex_exec_args`) and Fails with Codex's API error when the model is rejected; with no `agent_settings.codex.prompt_model` set it is `info` — drafting then uses the model configured in Codex itself, which the login check already vouches for. Detection is a **filename scan** of `~/Library/Fonts`, `/Library/Fonts` and `/System/Library/Fonts` (each one level deep, for `Supplemental`) — on Windows `%LOCALAPPDATA%\Microsoft\Windows\Fonts` (per-user installs) and `%WINDIR%\Fonts`, where Windows 11's stock `CascadiaCode.ttf` makes the default stack's fallback an `info` — comparing normalized names (lowercased, non-alphanumerics dropped) with the family as a *prefix* of the file name — a font file is named for the family plus its style (`JetBrainsMonoNerdFont-Regular`). That beats CoreText (a new dependency) and `system_profiler SPFontsDataType` (seconds slow) for something that sits in a health run. A missing preferred font is **`info`, never a failure**: the stack degrades to a stock face, so all that's lost is Claude Code's box/powerline glyphs. It carries a `brew install --cask …` remediation from a small **verified table** (`font_install_command`) rather than a derived name — a cask name can't be computed from a family (`JetBrainsMono Nerd Font` ships as `font-jetbrains-mono-nerd-font`), and an unknown family gets no command instead of a wrong one. Windows gets no command at all (`font_install_command` returns `None` there): Nerd Fonts have no official winget package. The one `warn` is the genuinely broken case: *no* family in the configured stack is installed. `terminal_font_check(stack, installed)` is split from the scan so every branch is unit-tested. Across the three tool-resolving checks (**git available**, **agent logged in**, **session editor**), because a `tool_paths` override is authoritative (see `docs/tool-resolution.md`), a configured-but-missing pin is a hard **fail** naming the path (`tool_not_found_detail` → `tools::stale_override`), *not* a silent fall-through to a PATH binary — the whole point of pinning is honored. (For the editor this fail takes precedence over the VS Code.app-present `warn`.)

**Tool versions is a trailing group, not a per-tool sub.** The earlier checks (**git available**, **claude logged in**, **terminal host available**) confirm each directly-invoked CLI *resolves*; this last group asks how old it is. mAIestro Code leans on features only newer releases have — Claude Code's `--remote-control`/`--name` launch flags, the `PostToolUseFailure` hook, `/color`; `git worktree`; VS Code's `--disable-workspace-trust` — so a stale binary can fail mid-spawn or degrade silently. It runs `<tool> --version` for the repo's agentic coding CLI (`claude` or `codex`), `git`, and — when the repo's sessions open in VS Code — `code` (or `cmux`, floor 0.65.0, when they open in cmux; or Windows Terminal, floor 1.24.0, when they open there) (same resolution as everything else — a `tool_paths` override is checked verbatim) and compares the first `digits(.digits)*` run on the first non-empty line of output (`parse_version`) against a **hardcoded** floor per tool (`MIN_TOOL_VERSIONS`, with the reason it exists) using component-wise comparison that treats a missing trailing component as `0` (`version_at_least`) — no `semver` dependency for three known output shapes. Below the floor is a **`warn`, never a `fail`**: an old tool might still work, and this report is informational like the rest of it; the detail names both versions and the reason, `claude` gets a `claude update` remediation and `codex` a `codex update` one (the Codex floor, 0.133.0, is the release where hooks went stable with `PermissionRequest`/`SessionEnd`), while `git` gets `brew upgrade git` only when the resolved binary actually lives under a Homebrew prefix (Apple's Xcode-stub git can't be upgraded that way) — `code` never gets one since it updates itself from its own menu. A tool `find_tool` couldn't resolve reports its version sub as `skipped` rather than repeating the failure the earlier row already surfaced at the right severity; output that ran but didn't parse (an unexpected wrapper) is `info` with a snippet of the raw text, since it isn't a known problem. Floors are a code change, not a setting — there is no `tool_paths`-style per-tool minimum override, and this is "old enough to break", not "not the newest" (no network call to check for a newer release). Windows Terminal is the exception to `<tool> --version`, which would open a dialog: its version is read without starting it (`windows_terminal::installed_version`) — `wt.exe`'s file version when `wt` is a real file (a pin to a portable copy), else the installed `Microsoft.WindowsTerminal` package's (`PackageManager`) — and when neither is known the row is `info`, as for an unparsable version.

**GitHub permission testing is the notable one, and it never mutates the repo.** mAIestro Code's own GitHub calls need read (repo/issues/PRs) *and* write (create/update issues, comments, assignees, create/merge PRs), so token validity alone isn't enough — but there's no side-effect-free "test this write endpoint" call. So write access is **derived, not exercised** (no throwaway issue/PR/label):
- **Token valid** — `GitHub::check_token()` does a raw (non-ETag-cached) `GET /user`, returning the login *and* the `X-OAuth-Scopes` response header. This is the only addition to `plugins/github.rs`.
- **Repo readable** — `GitHub::repo()` (`GET /repos/{owner}/{name}`), which also carries the `permissions` object.
- **Write access** — for a **classic PAT** (non-empty `X-OAuth-Scopes`) the scope list is authoritative: needs `repo` (or `public_repo` on a public repo). For a **fine-grained PAT** (empty scopes header) it reads the repo response's `permissions.push` flag. Either way the verdict ("token can read but cannot push to this repo") is inferred from what GitHub already reports.

The check uses the repo's assigned `identity_id` to pick the token (`GitHub::for_identity`); a repo with no identity assigned makes the GitHub check `skipped`. Out of scope for now: no live write probe, no `gh` CLI check, no auto-fix, and no background/periodic polling (runs only on button click).

**Checks are chosen per agentic coding CLI.** Only the repo's effective agentic coding CLI is checked: a Codex repo doesn't run the Claude probe, doesn't list `claude` in the tool checks, and doesn't version-check it (`tool_applies` filters `MIN_TOOL_VERSIONS`), and a Claude repo doesn't mention `codex` or `agy`. `git` and `code` are always checked.

**Antigravity** has no login-status command. The "Antigravity logged in" row runs `agy models` instead (`check_antigravity`, classified by the pure `antigravity_checks`). It starts no model turn and spends no quota:
- **Logged out:** `agy models` exits 1 at once with "Please sign in…". That is a login Fail whose fix is running `agy` to sign in.
- **Logged in:** it lists `id\tName` per model. The login Passes, and the **model available** sub-row checks the drafting model (`agent_settings.antigravity.prompt_model`) against that list. `agy` has no aliases, so an id without its effort suffix (e.g. `gemini-3.8-flash` for `gemini-3.8-flash-low`) fails with the available ids.

The version floor is `agy` **1.2.10**, which fixed the headless exit codes and JSON error output that drafting relies on. The upgrade command is `agy update`.

**Copilot** has neither a login-status command nor a per-account model list. The "Copilot logged in" row runs one tiny tool-less call exactly as drafting does: the prompt on stdin, `--available-tools none`, in `~/.maiestro/copilot-draft/` (`check_copilot`, classified by the pure `copilot_checks`). It costs one premium request:
- **Not found:** `copilot` doesn't resolve. When VS Code's Copilot Chat shim is the only `copilot` on PATH, the detail says so and how to install the real CLI (`npm install -g @github/copilot`, or run `copilot` once in a terminal and accept its install prompt). The shim itself is never run.
- **Logged out:** `Error: No authentication information found.` The fix is `/login` in `copilot`, or `gh auth login`, since Copilot also uses the `gh` token.
- **Bad model:** `from --model flag is not available` → the login Passes and the model row Fails. Which models work depends on the Copilot plan.
- **`node` missing:** `env: node: No such file or directory` → the npm install's Node loader can't start.
- **No Copilot access:** a subscription/access error fails the login row with Copilot's message.
- **Clean run:** the stream must pass drafting's fail-closed parser (the "Disabled tools:" confirmation, no tool execution). With no drafting model set, the model row is Info and names the model Copilot's automatic routing picked.

The version floor is `copilot` **1.0.90**, the version the Copilot support was verified on. The upgrade command is `copilot update`. A machine with only one agentic coding CLI installed therefore gets a clean report for repos on that agentic coding CLI.
