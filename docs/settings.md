# Settings

Everything that lives in `~/.maiestro/` besides identities and status files: per-repo settings, global app settings, their JSON Schemas, the Settings window forms that edit them, launch at login, and the About block.

## Per-repo settings

Each repo tracked by mAIestro Code has a small settings record stored in `~/.maiestro/repos/<owner>-<name>.json`. This is the place for configuration that is specific to a repo but not a credential. The file is human-editable and dotfile-manageable.

**Tracking a repo requires no affiliation with it.** A tracked repo is just one of these files, keyed by `owner/name`, and every downstream path (dashboard, issue list, spawn, PR flow) works for any repo the assigned identity's token can *read*. The Settings window's Add Repo picker therefore offers two ways in: browsing `github_list_repos` (`GET /user/repos`, affiliation `owner,collaborator,organization_member`), or typing an arbitrary `owner/name` into the picker's filter box, which doubles as manual entry and offers an "Add …" row for anything shaped like `owner/name` that the fetched list doesn't already contain. Opening the picker **auto-loads** the repo list for the default identity (or the only/first one) — there is no Fetch button; the identity select stays at the top and re-fetches on change, discarding a late response for an identity the user has already switched away from. Manual entry is offered even while that list is still loading, so naming a repo outright never waits on the fetch. The typed name is validated through `github_get_repo` (`GET /repos/{owner}/{name}`) before the settings file is written, so a typo fails at add time rather than becoming a broken dashboard row, and GitHub's canonical `full_name` — not the typed string — is what gets tracked, normalizing case. What an external repo does *not* get is push access it never had: the spawn path's issue assign/comment steps are already non-fatal warnings, and the health check already reports "token can read but cannot push". Contributing through a **fork** (pushing to the fork, cross-repo PRs) is not supported — the spawn/PR flow assumes push access to the tracked repo itself.

Current schema:

```json
{
  "cloned_repo_dir": "~/src/repo-name",
  "worktree_prefix": "~/src/work-",
  "repo": "owner/repo-name",
  "identity_id": "personal",
  "env_files": [".env", "frontend/.env.local"],
  "post_spawn_commands": ["pnpm install"],
  "comment_on_spawn": true,
  "delete_remote_on_teardown": true,
  "agent": null,
  "prompt_models": { "claude": "haiku", "codex": null, "antigravity": "gemini-3.8-flash-low" },
  "hidden": { "snooze_until": 1717372800000 },
  "prompts": { "draft_issue": null, "short_label": null, "draft_pr": null }
}
```

- **`cloned_repo_dir`**: absolute path to the local git clone (the primary checkout). Defaults to `~/src/<repo-name>` (no owner prefix). The source clone `git worktree add` runs in, and the root for env file scanning.
- **`worktree_prefix`**: prefix for spawned worktree locations. The full worktree path is `<worktree_prefix><workspace>/<repo>` — a string concatenation, so the trailing `work-` is part of the directory name, not a separate path component (e.g. `~/src/work-12-add-foo/repo-name`). Absent/`null`/empty falls back to the schema `default` (`~/src/work-`). Tilde-expanded. Changing it affects future spawns only; it does not move existing worktrees.
- **`env_files`**: ordered list of env files, **relative to `cloned_repo_dir`**, copied into a freshly-created worktree right after `git worktree add` (gitignored files don't travel with the worktree, so the copy is what carries them over). Populated via a "Scan" action that walks the cloned repo directory (up to 4 levels, skipping `node_modules`, `.git`, `target`, etc.) looking for files named exactly `.env` (variants like `.env.local` aren't auto-scanned — add those by hand). Users can also add or remove entries manually.
- **`post_spawn_commands`**: ordered list of shell commands run in a **freshly-created** worktree right after `git worktree add` (and env-file copy / hook setup), before the editor opens — e.g. `pnpm install`. Empty by default. Run by `run_post_spawn_commands` in `spawn.rs` via the user's login shell (`$SHELL -lc`) so PATH and tool managers (nvm/pnpm/asdf) are available (mAIestro Code's own env is minimal). They run in order, stop at the first failure or a 10-minute per-command timeout, and surface a `SpawnResult.warnings` entry on a problem — the worktree is never torn down for a command failure. The reuse-existing-worktree spawn path does **not** run them (nothing new was created).
- **`comment_on_spawn`**: whether spawning a workspace posts a comment on the issue recording the branch, the local directory, and the session label. Absent/`null` = the schema `default` (`true`, today's behaviour); `false` keeps the spawn entirely local to you. Read in `do_finish_spawn` (`spawn.rs`) via the `SpawnBg` record. It gates **only** the comment — the issue is still assigned to the token's user, which this setting deliberately does not control (turn assignment off by not spawning). Like the comment itself, a failure here is a non-fatal `SpawnResult.warnings` entry.
- **`delete_remote_on_teardown`**: whether tearing down a workspace also deletes its branch on GitHub, so merged work doesn't leave stale branches behind. Absent/`null` = the schema `default` (`true`). The delete is `DELETE /repos/{repo}/git/refs/heads/<branch>` via `GitHub::delete_ref`, which treats `404`/`422` ("Reference does not exist") as success — GitHub deletes a merged PR's head branch itself when the repo has that option on, so "already gone" is the common case, not an error.

  **The setting enables the delete; it never overrides the safety guard.** `spawn::remote_delete_skip_reason` is a *whitelist*: the branch is removed only when the setting is on, **no pull request is still open** against it, and either GitHub confirms a PR merged it or the branch demonstrably carries nothing the base lacks. A branch holding unmerged commits is always left alone — including when the user confirms through teardown's warnings prompt, since confirming the destruction of a *worktree* is not consent to destroy pushed commits that, once the worktree is gone, exist nowhere else. There is no force/override path; such a branch is deleted on GitHub by hand. Every skip is logged at `info` with its reason.

  **Merged-ness is asked of GitHub, never inferred from local ancestry.** `merged_at` on the PR is authoritative however the PR landed. A squash- or rebase-merged PR leaves *no commit of its own* as an ancestor of the base, so `git branch --merged`, `merge-base --is-ancestor` and `rev-list --count <base>..<branch>` all report such a branch as unmerged and would strand it forever. Hence the `Landed` tri-state (`spawn.rs`): `Yes`/`No` are GitHub's answer, and `Unknown` — no identity, or the API call failed — is kept distinct so a swallowed network error can never read as a confident "not merged".

  **Both uncertainties fail closed.** `Landed::Unknown` blocks the delete, and so does a `None` from `unmerged_commit_count` (git couldn't count, e.g. a missing `origin/<base>`). The two directions aren't symmetric: keeping a stale branch is untidy, deleting a live one destroys work. The local count itself uses **`git cherry`**, which compares *patch ids* rather than ancestry, so a branch that landed by rebase, cherry-pick, or a single-commit squash counts as 0. Known limit: a **multi-commit** squash still counts > 0, because the squashed patch matches no individual commit — that only matters for work landed *without* a PR (GitHub's `merged_at` covers the PR case), and it fails safe by keeping the branch. Teardown also runs a best-effort `git fetch` first, so a stale `origin/<base>` can't inflate the count.

  The whole step is **non-fatal**: a failed delete warns and teardown still reports `Done` — an unreachable GitHub must never strand a worktree. Independently of it (and even when the guard skips), teardown drops the now-stale remote-tracking ref with a local `git update-ref -d refs/remotes/origin/<branch>`, which costs no network and cleans up after GitHub's own merge-time deletion too.
- **`agent`**: the agentic coding CLI for this repo — `"claude"` (Claude Code), `"codex"` (Codex CLI) or `"antigravity"` (Antigravity CLI, binary `agy`). `null`/absent = the global `agent` setting, then its app-schema `default` (`claude`); resolved by `repo_settings::effective_agent`, which **every** AI call site goes through (issue/label drafting, the PR draft, the Check Health probe, and a fresh spawn). One repo means one agent: it runs both the session launched into each worktree and mAIestro Code's own drafting. The spawn stores the agent on the session record (`Session.agent`), so changing this later never switches an existing worktree to the other agent on reopen — but mAIestro Code's own drafting calls, including the PR draft for an older worktree, follow the repo's **current** agent. Only the agentic coding CLI in use needs to be installed. The Settings form renders an **Agentic Coding CLI** select whose first option, "Use global default (…)", names the agent `null` resolves to.
- **`prompt_models`**: which model runs mAIestro Code's **own** programmatic prompts (`draft_issue`, `short_label`, `draft_pr`), **per agentic coding CLI** — only the entry for the repo's effective agentic coding CLI is used. Resolved by `prompts::model(models, agent)` and passed through `drafting::agent_text`'s single `--model` choke point. `claude`: `null`/empty = the schema default (`haiku`), passed **verbatim** to `claude --model`, so a tier alias (`haiku`, `sonnet`, `opus`, `fable`) or a full model id works; an alias auto-tracks the latest model in its tier. `codex`: `null`/empty = the schema default `null`, meaning **no `--model` at all** — Codex uses the model configured in Codex itself; any value `codex exec --model` accepts works. `antigravity`: `null`/empty = the schema default `gemini-3.8-flash-low`, passed as `agy --model`. `agy` has no tier aliases, so this must be an id from `agy models`, including its effort suffix (`-low`/`-medium`/`-high`), and Check Health verifies it against that list. None is a closed schema enum, so a new model needs no mAIestro Code update. The form's "Prompt model" field edits the entry for the repo's effective agent (switching the Agentic Coding CLI select swaps which entry shows) and *suggests* models for that agent, **asked of the CLI itself** where it can list them: the `agent_models` command (`backend/src/models.rs`) runs `codex debug models` (the user-selectable `visibility: "list"` slugs, in Codex's priority order) or `agy models` (the ids the signed-in account can use), caching a successful list per agent for 10 minutes. Claude Code has no listing command, and a missing, signed-out, slow (20s timeout) or unparsable CLI returns `null`, so the field falls back to the built-in `PROMPT_MODEL_SUGGESTIONS` hints (Claude's tier aliases, and a snapshot of each other catalog) — the built-in list shows at once and is swapped for the queried one when it arrives; a bad value fails at draft time (surfaced, non-fatal). Applies **only** to these drafting calls — never to the user-facing session launched in the worktree, which uses the user's own agent config.

  **Migration from `prompt_model`.** Files written before issue #162 carry a single `prompt_model` (a `claude --model` alias). `parse_and_validate` reads it once as `prompt_models.claude` (an explicit `prompt_models.claude` wins) and drops the old key, so a custom drafting model isn't lost and the next save writes only the new shape.
- **`hidden`**: repo-level hide/snooze state. Absent (or `null`) means visible. When present, the repo and all its work items are hidden from the dashboard unless "Show hidden" is toggled on. `snooze_until` is a Unix-epoch-millis timestamp the repo stays hidden until (`null` = hidden indefinitely); once that time passes the repo renders as visible again. Per-work-item hide state is **not** stored here — it lives on each session record (`~/.maiestro/sessions/<id>.json`).
- **`prompts`**: per-repo overrides for the AI prompt instructions mAIestro Code sends to the repo's agentic coding CLI (`backend/src/prompts.rs`). They don't depend on which agentic coding CLI it is. Three fields, each `null`/empty = use the built-in default: `draft_issue` (idea → GitHub issue), `short_label` (issue → short workspace label), `draft_pr` (diff → PR description). Each prompt is assembled as `<instruction> + <runtime context>`: the **instruction** is what these overrides (or the defaults) supply; the **runtime context** (your idea, the issue title/body, the diff) is appended by the drafting/PR code (`drafting.rs`/`pr.rs`) and is *not* configurable, so an override — even arbitrary text or a `/skill` invocation — can't drop the data the draft needs. The Settings form shows each prompt's default text in a paragraph (textarea) field for editing.

**Defaults live in the JSON Schema only.** The `worktree_prefix`, `prompt_models.*`, `comment_on_spawn`, `delete_remote_on_teardown`, and `prompts.*` defaults are declared as JSON Schema `default` keywords in `repo-settings.schema.json` and read from there by both sides — the backend via `repo_settings::schema_default("/properties/.../default")` (JSON Pointer into the embedded schema), or `schema_default_bool`/`bool_or_default` for the boolean ones, and the Settings form via `extractFormDefaults` (the form strips `default` before handing the schema to JsonForms so it doesn't auto-inject them into the null-means-use-default fields). There is no hardcoded copy of these defaults in Rust or TS.

That stripping is why the form's boolean switch needs the default explicitly: a `null` boolean would otherwise render as *off* while the effective value is *on*. `extractFormDefaults` therefore collects **every** boolean property's default into `booleanDefaults`, keyed by property name, and the switch shows `data ?? booleanDefaults[path]`. It is collected generically rather than field-by-field, so a boolean added to the schema needs no frontend edit.

**Soft path validation + Finder reveal.** Every path-referencing field in the Settings window (`cloned_repo_dir`, `worktree_prefix`, each `env_files` entry; and `tool_paths` in global settings) gets a light-touch existence check and a folder-icon **reveal-in-Finder** button, via the shared `frontend/src/PathField.tsx` (the `usePathExists` hook, `RevealButton`, `PathMissingHint`). The check is **advisory only** — it debounces a call to the `path_exists` command and shows an inline "not found" hint, but does *not* feed ajv/schema validation, so it never blocks the debounced autosave. The reveal button (disabled when the path is empty or missing) calls `reveal_path`, which is `open -R` (reveal-and-select, so an env *file* is selected rather than launched) — distinct from `open_path`'s bare `open`. Both commands live in `links.rs` and tilde-expand via the shared `paths::expand_tilde`. Two fields aren't validated as-is because they aren't standalone paths: `worktree_prefix` is a string prefix (never a real path), so its check/reveal targets the **parent directory** (`~/src` for `~/src/work-`); and `env_files` entries are **relative to `cloned_repo_dir`** (the backend copies them from `cloned_repo.join(rel)`), so each is resolved against the repo's cloned repo dir before checking. Both resolutions are computed frontend-side.

`usePathExists` only re-runs on its own when the field's *value* changes, which would otherwise leave a "not found" hint stale after the user fixes the underlying problem outside the field (most commonly: running a Check Health remediation command in a terminal). `Settings.tsx` also holds a `probeGeneration` counter, provided to every path field via `PathProbeGenerationContext` (default `0`, so the hook works unchanged wherever the provider is absent); `usePathExists` includes that generation in its effect dependencies, so bumping it re-probes every mounted path field — and re-resolves `tool_paths` via `api.toolsResolved()` for the Tool paths status line — without reloading or re-seeding either form's settings data (see "The health check modal re-probes path/tool hints on close" in `docs/health-check.md`).

## Per-repo schema and validation

The file format has a hand-written JSON Schema, checked in at `backend/schemas/repo-settings.schema.json`. It is the **spec** for the format — deliberately *not* generated from the Rust `RepoSettings`/`HideState` structs. We chose a stable, human-authored artifact (with its own field descriptions) over `schemars`-style generation; the drift risk generation would have eliminated is instead caught by a test. `backend/src/repo_settings.rs` embeds the schema with `include_str!`, and the `repo_settings_schema` Tauri command returns it to the Settings window's JSON Forms renderer.

- **Drift guard (`schema_matches_struct` test).** A unit test serializes a default and a fully-populated `RepoSettings`, asserts both validate against the embedded schema, and asserts the schema's top-level `properties` key-set equals the serialized field-set. Adding a field to the struct *or* the schema without the other fails `cargo test`. This is what keeps the hand-written schema honest.
- **Load-time validation (`load_validated`).** Reading a settings file now validates it (via the `jsonschema` crate) before deserializing, with three outcomes: **missing** → defaults (unchanged); **invalid** (bad JSON or a schema violation) → a loud `Err` naming the file and the failing field; **valid** → the parsed settings. `repo_settings_get` is therefore fallible (`Result<RepoSettings, String>`) and its call sites across the spawn/draft/PR paths (most now routed through `repo_context::repo_context`) propagate the error, so a spawn fails loudly rather than silently running with a wrong `cloned_repo_dir`. `repo_set_visibility` errors instead of clobbering an unparseable file with defaults, and `repo_settings_set` validates the value before writing (defense in depth). The Settings window shows a load failure as a banner instead of a form full of defaults. `repos_list` stays lenient (a single malformed file shouldn't drop the repo from the list).
- **Unknown fields are tolerated** (`additionalProperties` is not `false`), so a file written by a newer app version still loads in an older one, and a hand-edited `$schema` key is allowed.
- **Editor autocomplete.** The schema ships as a Tauri bundle resource at `mAIestro Code.app/Contents/Resources/schemas/repo-settings.schema.json`, so a hand-editor can point a `$schema` key at it for autocomplete in VS Code (for an installed app: `/Applications/mAIestro Code.app/Contents/Resources/schemas/repo-settings.schema.json`). It is a build artifact versioned with the binary — the app deliberately does **not** write it into `~/.maiestro/`, which holds only user-editable configuration. In a dev checkout, point `$schema` at `backend/schemas/repo-settings.schema.json` directly.

The Settings window's repo detail form is rendered by **JSON Forms** (`@jsonforms/{core,react,vanilla-renderers}`) from the fetched schema plus a hand-written UI schema (`frontend/src/RepoSettingsForm.tsx`) that orders the fields and hides `repo`/`hidden`. Custom renderers cover what the schema can't express: an **identity select** (options from the live identity list), an **agentic coding CLI select** (whose "Use global default" option names the resolved global agentic coding CLI), a **per-agentic-coding-CLI prompt-model** field, an **env-files** list (Scan/Add/Remove), and a generic **boolean** renderer that replaces the vanilla checkbox with the same on/off switch the General panel uses (the switch itself is the shared `frontend/src/components/ToggleSwitch.tsx`, so the two forms can't drift apart). The boolean renderer is registered by type (`isBooleanControl`), not by field name, so it picks up any boolean the schema gains. The frontend strips `$schema`/`$id` before handing the schema to JSON Forms so its bundled draft-07 ajv compiles cleanly; the backend still validates with the real draft 2020-12. Saving is debounced autosave-on-change, blocked while ajv reports errors.

## Global app settings

App-wide settings that are neither a credential nor repo-scoped live in `~/.maiestro/settings.json` (`backend/src/app_settings.rs`), a sibling of `identities.json`. Like the other `~/.maiestro/` files it is human-editable and dotfile-manageable; every field is optional, so a missing or partial file falls back to defaults.

Current schema:

```json
{
  "window": { "width": 680, "height": 460 },
  "settings_window": { "width": 720, "height": 520 },
  "theme": "system",
  "agent": "claude",
  "terminal_font_family": null,
  "tool_paths": { "claude": null, "codex": null, "agy": null, "git": null, "code": null },
  "launch_at_login": false,
  "onboarding_completed": false,
  "update_check": {
    "checked_at": "2026-09-24T14:02:11+00:00",
    "latest_version": "0.4.0",
    "latest_published_at": "2026-09-10T18:30:00+00:00",
    "dismissed_version": "0.4.0"
  }
}
```

Like per-repo settings, the file format has a **hand-written JSON Schema** (`backend/schemas/app-settings.schema.json`), embedded via `include_str!` in `app_settings.rs` and returned by the `app_settings_schema` command. A `schema_matches_struct` drift-guard test keeps the schema and the `AppSettings`/`ToolPaths` structs in sync, and `load_validated` surfaces a corrupt file as a loud error (a banner in the Settings window) instead of silent defaults. **No writer merges into a corrupt file either**: every partial write (`app_settings::update` — the window-size persisters, onboarding, the General form, the update check and its dismiss) loads strictly first, and when the file is present but unparsable or invalid it logs an `error` ("refusing to write settings.json over an unreadable file") and returns it, leaving the file byte-for-byte as it was. Only the lenient `load()` (hot-path reads such as the theme and tool paths) falls back to defaults, and it never feeds a write. This is what turns a hand-edit typo — a trailing comma, a missing brace — into a visible banner and a log line rather than a file silently reset to defaults on the next popover resize or update check. The **popover** shows it too: `MainView` polls `app_settings_problem` (the `load_validated` error plus the file's path, `None` when the file is fine or absent) on every show and renders a red `SettingsProblemBanner` under the header — "Couldn't read settings.json: …" with a **Reveal** button (`reveal_path`) — which disappears on the next open once the file is fixed. Unknown fields are tolerated for forward-compat. The **General** panel in the Settings window renders this schema with **JSON Forms** (`frontend/src/AppSettingsForm.tsx` — UI schema + a custom theme renderer, an agentic coding CLI renderer, a launch-at-login toggle renderer, and a custom tool-paths renderer), autosaving on change like the repo form. (`onboarding_completed` and `update_check` are machine-managed and hidden from the form.)

**The panel re-reads the file on every open.** The Settings webview is created at app startup and only *hidden* when closed (`useHideOnClose`), so the values it fetched on mount would otherwise stand for the life of the process — and its mount happens *before* the first-run onboarding dialog has been answered, so a launch-at-login chosen there would leave the General toggle showing the stale `false` (and the next autosave would write that stale value back, undoing the LaunchAgent). Both entry points into the window — the tray menu's **Settings** item and the popover's gear button, the latter via the `open_settings` command rather than `show()` in JS — therefore go through `show_settings` in `main.rs`, which emits a **`settings-shown`** event on each hidden → shown transition; `Settings.tsx` listens and re-runs `loadAppSettings()` (settings, tool resolution, About), re-seeding the autosave baseline so the reload can't save itself back over the file. This mirrors the popover's `popover-shown` refresh. The event fires only on a real transition, so clicking Settings while the window is already open never reloads the form out from under an edit in progress. Hand edits to `settings.json` are picked up the same way, on the next open.

- **`window`**: persisted size (logical pixels) of the menu-bar popover (the `main` window). The popover is undecorated/transparent and `resizable: true`; the user drags invisible edge/corner grips (`ResizeGrips` in the frontend, forwarding to Tauri's `startResizeDragging`). The backend restores this size in `setup()` *before* the first show (so there's no resize flash) and saves the current size in the blur handler when the popover hides — a low-churn save point versus writing on every drag frame. A restored size is clamped to the `minWidth`/`minHeight` in `tauri.conf.json` (mirrored as `MIN_POPOVER_*` constants in `main.rs`). Absent `window` means "use the `tauri.conf.json` default size." Window **position** is not persisted — on each show `position_popover` (`main.rs`) anchors the popover under the tray icon, on **the display whose menu bar was clicked**, and clamps it into that display's bounds so it always shows fully on-screen, never cropped when the tray icon sits near the far-right edge or after the popover has been resized wider. If the persisted size is larger than the display (a stale/huge saved size, or a small monitor), the popover is first **shrunk to fit** so it can't overflow. It always drops *down* from the icon (`y = tray bottom`), since the macOS menu bar is at the top of its own display wherever that display is arranged. Machine-managed: modelled in the schema but hidden from the JSON-Forms UI (like `settings_window`). **All placement math is in macOS points** (`backend/src/popover_placement.rs`, a pure, unit-tested module), applied with `LogicalSize`/`LogicalPosition` (#175). macOS has one global point space, but tao and tray-icon hand it to us as "physical" px scaled by *different* factors: the tray rect by the clicked display's scale, each monitor's bounds by its own, the cursor by the primary display's, and `set_position(Physical…)` divides by the popover's *current* display's. On a mixed-DPI setup (Retina laptop + 1× external) mixing those put the popover on the wrong display, so every input is first normalized back to points. The tray rect's scale is unknown, so each tray event also records the cursor in points (`TrayCapture` in `PopoverState`); the pointer is over the icon at that moment, so it identifies the tray's display unambiguously (dividing the rect by each display's scale alone can match two displays). The placement is computed analytically and applied in one `set_position` before `show()`, rather than read back from the live window, whose geometry lags a cycle on macOS. `position_popover` logs each placement (tray rect, display, scale, position) at `debug`. Before any tray rect has ever been cached (e.g. the very first show right after onboarding, or a single-instance relaunch before the user has hovered/clicked the tray icon), the popover is pinned to the top-right corner of **the display under the cursor** (falling back to the main display) with an `8`pt margin (`TOP_RIGHT_MARGIN`), approximating where the tray icon itself lives, rather than dead-centering it. This deliberately isn't the positioner plugin's own `move_window(TrayCenter)`: that panics ("Tray position not set") when *its own* internal tray cache — populated only by `on_tray_event`, separate from our `PopoverState.tray` — is also empty, which is exactly the case here.
- **`theme`**: chosen UI appearance — `"light"`, `"dark"`, or `"system"`. Absent means `"system"`. Set via the **General** panel's theme control, read on launch by every window (`app_settings_get_theme`, `frontend/src/theme.ts`). Each webview applies the theme to its own `<html>`: an explicit choice sets `data-theme="light|dark"`, while `"system"` removes the attribute so the `prefers-color-scheme` media query in `styles.css` follows the macOS appearance live. `app_settings_set` broadcasts a `theme-changed` event so the popover, Settings, and Logs windows re-apply without a restart. `app_settings_set` load-merges — the form owns `theme`/`tool_paths`, while the machine-managed window sizes are kept from disk, so persisting one never clobbers the other.
- **`agent`**: the default agentic coding CLI — `"claude"`, `"codex"` or `"antigravity"` — for repos whose own `agent` is `null`. `null`/absent = the schema `default` (`claude`), read via `app_settings::agent()`, so an install that never picks one behaves exactly as before issue #162. Edited with the **Default Agentic Coding CLI** dropdown (Claude Code / Codex CLI / Antigravity CLI) in the **General** panel, the same control as the per-repo Agentic Coding CLI field minus its "Use global default" option; owned by the form in `app_settings_set`'s load-merge.
- **`tool_paths`**: per-tool CLI path overrides — `claude`, `codex`, `agy`, `git`, `code`. Each `null`/empty = auto-resolve; a value pins that binary. Read by `tools::resolve_tool` (see `docs/tool-resolution.md`). Edited in the **General** panel, where each field shows the auto-resolved path as a placeholder and a live status line (`tools_resolved`) beneath it. The panel's rows are **generated from the schema** — one per `tool_paths.properties` entry, in declaration order, with the property key as the tool name and its `description` as the help line under the input. The custom renderer keeps no list or copy of its own, so a tool added or re-worded in the schema needs no frontend edit; the descriptions are therefore written as user-facing prose, serving both the General UI and someone hand-editing `settings.json`.
- **`terminal_font_family`**: the font stack written as `terminal.integrated.fontFamily` into each spawned worktree's `.vscode/settings.json`. `null`/empty = the schema `default` (`'JetBrainsMono Nerd Font', 'Cascadia Code', Menlo, monospace`), read via `app_settings::terminal_font_family()` — the schema is the only place that value lives, and the General field shows it as the input's placeholder (`extractAppFormDefaults`), never as pre-filled data. Claude Code's TUI draws box/powerline glyphs, so the default prefers a Nerd Font; neither preferred face ships with macOS, so the chain ends at **Menlo** (present since 10.6, VS Code's own macOS default) rather than the generic `monospace` alias. Applies to worktrees on their next spawn *or reopen* (`refresh_vscode_files` regenerates both `.vscode` files), so changing it re-themes existing workspaces too.
- **`launch_at_login`**: whether mAIestro Code starts automatically at login. Absent means `false`. Toggled by the on/off switch in the **General** panel and applied via `tauri-plugin-autostart`, which writes/removes a per-user LaunchAgent (`~/Library/LaunchAgents/mAIestro.plist`). See "Launch at login" below.
- **`onboarding_completed`**: machine-managed flag recording that the one-time onboarding flow has run. Absent/`false` = not yet onboarded; set once (to `true`) when the onboarding dialog is dismissed so it never reappears. Gates the first-run onboarding window (see "Launch at login" below). Modelled in the schema but hidden from the JSON-Forms UI (like `window`/`settings_window`). A standalone gate — not derived from any single preference — so onboarding can add options without changing what marks it done.
- **`update_check`**: machine-managed state of the background update check (`docs/update-check.md`). `checked_at` is when the last successful check ran; `latest_version` / `latest_published_at` are the newest published release it saw; `dismissed_version` is the version whose banner the user dismissed (hidden for exactly that version, shown again for a newer one). Absent = never checked, nothing dismissed. Written only by `update_check.rs` through `app_settings::update`, kept from disk by `app_settings_set` (like the window sizes), and hidden from the JSON-Forms UI. Every value is a string so a hand edit that isn't valid RFC 3339 or semver degrades to "unknown" at the point of use rather than failing the settings load.

## About (version + build info)

The **General** panel ends with a read-only **About** block showing the running app's version, whether it is a release or a development build, its build date, the short git SHA it was built from, and a **Release notes** button that opens `https://github.com/yanokamay-org/maiestro/releases/tag/v<version>` in the browser (via `links::open_url`). Its text is selectable (the `.panel` shell sets `user-select: none`, so `.about-lines` opts back in) so a version can be pasted into a bug report.

It is **not a setting.** None of it lives in `~/.maiestro/settings.json` or `app-settings.schema.json` — adding it there would fail the `schema_matches_struct` drift guard and the form's autosave would try to write it back. It is served by its own command, `about::app_version` (`backend/src/about.rs`), and rendered as plain markup after the JSON Forms block (`frontend/src/components/AboutSection.tsx`), so a failed fetch hides the block instead of blocking the General panel.

Where each value comes from:

- **Version** — `app.package_info().version`, which Tauri fills from `backend/tauri.conf.json`'s `version`. That is the same file `scripts/release.sh bump` treats as the single source, so the displayed version can't drift from the release pipeline.
- **Build date / commit** — stamped at compile time by `backend/build.rs` as `MAIESTRO_BUILD_DATE` (UTC `YYYY-MM-DD`) and `MAIESTRO_GIT_SHA` (`git rev-parse --short HEAD`), read with `env!`/`option_env!`. No network call and no metadata file next to the binary. The SHA is optional — a build without git (a source tarball) simply omits it, and it gains a `-dirty` suffix when the tree had uncommitted changes at build time.
- **Release vs. dev build** — `scripts/release.sh build` runs `pnpm tauri build` with `MAIESTRO_RELEASE=1`, which `build.rs` turns into a `MAIESTRO_RELEASE_BUILD` stamp; anything else (`tauri dev`, a hand-run `pnpm tauri build`) is a **dev build** and sets `AppVersion.dev_build`. A dev build carries the *last released* version, so showing a bare `0.2.3` would claim to be that release — the About block instead renders `0.2.3+dev` with a "dev build" badge and the line "Local build, after the v0.2.3 release". The test can't be "is HEAD tagged `vX.Y.Z`?": `release.sh` builds **before** it tags (the tag is created by `publish`), so a genuine release build has no tag yet.
- **Caveat:** `tauri_build::build()` emits its own `cargo:rerun-if-changed` directives, which replace cargo's "rerun when any package file changed" default, so the build script does not re-run on every incremental `tauri dev` build and the stamped date can lag there. It is always correct for a release build, because `release.sh bump` rewrites both `tauri.conf.json` and `Cargo.toml`, forcing a re-run.

The About block itself is informational only — it does not say whether a newer version exists. That is the job of the separate background update check and the popover banner it drives, described in `docs/update-check.md`; there is still no auto-update.
## Launch at login

An opt-in **Launch at login** toggle in the **General** panel starts mAIestro Code automatically when the user logs in. It is backed by **`tauri-plugin-autostart`** with `MacosLauncher::LaunchAgent`, which writes/removes a **per-user LaunchAgent** at `~/Library/LaunchAgents/mAIestro.plist` (name pinned to `mAIestro` via the plugin builder's `app_name` rather than the productName, so the rebrand to mAIestro Code kept existing plists in place; `Label = mAIestro`, `RunAtLoad=true`, `ProgramArguments` = the current binary path). A LaunchAgent (not a LaunchDaemon) runs **as the logged-in user inside their GUI login session**, which is exactly what the Keychain-at-login and ambient-identity decisions require — root has no user/Keychain context. Like every other launch it inherits a minimal environment (no shell profile sourced), the same case `tools::init()` already handles by recovering the login-shell PATH; the plist passes no custom env or args. In macOS Ventura+ Login Items it appears under **"Allow in the Background"** (where LaunchAgents live), *not* "Open at Login" (GUI login items via a different API) — `launchd` loads the plist at login and `RunAtLoad` starts it. The baked `ProgramArguments` path is why the startup **reconcile** matters: a build re-`enable()`s to rewrite a stale dev-binary path (see below).

We call the plugin **only from our own Rust** (`app_settings::set_autolaunch` via `ManagerExt` — `enable()`/`disable()`/`is_enabled()`), never from JS, so no `capabilities/default.json` entry is needed. The preference lives in `~/.maiestro/settings.json` as `launch_at_login` (see "Global app settings" above); `app_settings_set` applies the OS change **before** persisting, so a failed `enable()`/`disable()` returns an error (surfaced as the form's banner) and the stored pref stays consistent with reality.

Two `setup()` hooks keep it honest, mirroring the hook-reconciliation pattern:
- **`reconcile_launch_at_login`** brings the plist into agreement with the stored pref on every launch. When the pref is on it unconditionally re-`enable()`s, which rewrites the plist with the current `current_exe()` — healing a stale path baked by a torn-down `tauri dev` build (release builds resolve to the stable `/Applications` path and stay fixed). `disable()` only fires when a plist actually exists, so reconciling-off is a no-op rather than a "file not found".
- **`maybe_show_onboarding`** runs a **one-time onboarding** flow, gated on the machine-managed `onboarding_completed` flag. It is a **branded webview window** (`onboarding`, defined in `tauri.conf.json`, rendered by `Onboarding` in `App.tsx` — routed by window label like `settings`/`logs`), **not** a native OS alert: an alert can only show the generic system icon and a fixed button set, whereas the webview shows the mAIestro Code **logo and name** and can grow more options over time. It is a **single wizard** (#189): a fixed shell — logo and name, a step rail, and a footer with the actions — around a step body that is the only thing that changes, so moving between steps never reads as a second window. Step 1, **Connect GitHub**, stores a first identity's token (skipped, along with the rail and **Back**, when an identity already exists); step 2, **Choose defaults**, puts the **default agent** and **Launch at login** on one screen. The agent picker is a radio list of every agent with a live **Installed / Not installed** status from `tools_resolved` (the agent's CLI — `agy` for Antigravity); it preselects the saved `agent`, else the schema default when installed, else the first installed agent, else the schema default, and picking an uninstalled agent shows install guidance rather than blocking. New preferences slot in as more rows on step 2 feeding the same submit. Right before `show()`, `maybe_show_onboarding` reads back the window's own native `theme()` (the real NSWindow/OS appearance, correct even while hidden) and re-asserts it via `set_theme`, then calls `set_background_color` with `DARK_BG`/`LIGHT_BG` — hardcoded to match `styles.css`'s `--bg` tokens. The actual flash isn't a theme mismatch: a window created hidden (`visible: false`) has painted nothing yet, so the instant it appears it shows its native window/webview background — white by default — until the CSS finishes loading a frame or two later. `set_background_color` fixes that directly by giving the window a themed backing color before anything is shown; `set_theme` is kept alongside it for native chrome (scrollbars, form controls) and to make `window.theme()` itself reliable. Both follow the raw OS theme here (not the app's own `theme` setting), which is correct because onboarding only ever runs before the user could have set an explicit Light/Dark preference. **Get started** calls the `onboarding_complete` command with both choices (which applies them via `complete_onboarding` — writing `launch_at_login` and `agent` — and `destroy()`s the window); closing the window's title bar instead accepts the defaults (launch-at-login off, `agent` left unset so the schema default applies) via `complete_onboarding_if_pending` (wired in `main.rs`'s window-event handler, guarded on the flag). Either way `onboarding_completed` (and any chosen prefs) are written, so it never reappears; existing users upgrading in are onboarded once. `complete_onboarding` ends by calling `main.rs::show_popover` (made `pub(crate)` for this), so finishing onboarding — either way — pops open the menu-bar popover rather than leaving the user looking at an empty desktop; the guard on `complete_onboarding_if_pending` means this only fires on a real completion, never on the belt-and-suspenders no-op. The choices land in `settings.json` after the (hidden) Settings window has already read it, which is why the General panel re-reads on each open — see "Global app settings" above. The whole feature is failure-tolerant — a plist error is logged, never fatal. (The `onboarding` window is listed in `capabilities/default.json` so its webview can use core IPC.)
