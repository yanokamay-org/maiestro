# Worktree theming

How a spawned worktree gets its color and emoji, and how that one color reaches the popover row, the session's window (VS Code, Terminal.app, cmux or Windows Terminal), and the Claude session. The code lives in `backend/src/theming.rs` (`pick_theme`, `claude_color`, `dark_tint`), `backend/src/editor.rs` (`write_vscode_files`) and `backend/src/terminal_app.rs`; the session command both terminal hosts run is `terminal_host::session_argv`.

A spawned worktree gets a deterministic color and emoji from `theming::pick_theme`, seeded by the workspace name and avoiding colors already claimed by tracked sessions. That one color is applied in three places so the visual thread survives from the dashboard to where the user actually works: the popover row, VS Code's title/status/activity bars (`editor::write_vscode_files`), and the Claude session's own UI.

`PALETTE` **is** Claude Code's session palette: the eight entries are the exact hex values Claude Code's standard theme paints its eight session colors with (`red, blue, green, yellow, purple, orange, pink, cyan`), in the order `/color` lists them. Using Claude's own values, rather than a hand-darkened approximation, is what makes the row, the bars, and the session read as one color (the old dark palette's "orange" read as brown next to Claude's terracotta). `theming::claude_color` is therefore a **bijection**: no two live sessions collide on a session color while a distinct one goes unused. Two unit tests enforce this — one for the bijection (a ninth palette entry fails the build rather than silently doubling up) and one pinning each hex to Claude's RGB value (a drifted hex fails rather than shipping a mismatched title bar).

| Claude color | Hex | Emoji |
|---|---|---|
| red | `#dc2626` | 🔴 🍒 🌶️ 🦞 🍓 |
| blue | `#6a9bcc` | 🔵 🫐 🦋 💙 🐳 |
| green | `#16a34a` | 🟢 🌿 🐸 🍀 🐊 |
| yellow | `#ca8a04` | 🟡 🍋 🌻 🐝 ⭐ |
| purple | `#827dbd` | 🟣 🔮 💜 🍇 |
| orange | `#d97757` | 🟠 🦊 🍊 🦁 🍑 |
| pink | `#c46686` | 🎀 🌸 🦩 🐷 🩷 |
| cyan | `#0891b2` | 🐬 🐠 🌊 🧊 🦚 |

Where the values come from: Claude Code ships as a single binary with its themes embedded, and each theme carries the session colors as `<name>_FOR_SUBAGENTS_ONLY` entries. To re-check them after a Claude Code upgrade:

```
strings -n 6 "$(readlink -f "$(which claude)")" | grep -o -E '(red|blue|green|yellow|purple|orange|pink|cyan)_FOR_SUBAGENTS_ONLY:"[^"]+"'
```

The `rgb(...)` blocks are the standard dark and light themes (they share one set of values, which is what the palette pins); the `ansi:` blocks are the ANSI themes and the remaining `rgb` blocks the daltonized ones, none of which we track.

`claude_color` is keyed off each session's **stored** hex and also maps every retired palette hex (the earlier dark palette, and the dark cyan that palette had itself replaced), so a session recorded under an older palette keeps the color it was given. `pick_theme` likewise avoids colors by their *Claude color* rather than raw hex, so an old-hex session still claims its session color against new spawns.

Because the palette is mid-tone rather than dark, `write_vscode_files` also pins a white foreground on the title, status, and activity bars: VS Code does not auto-contrast, and its theme default (light grey on dark themes, near-black on light ones) is unreadable on several of these backgrounds.

The color reaches the session as a **`/color <name>` initial prompt** appended to the launch command:

```
'/opt/homebrew/bin/claude' --remote-control --name '🎀 #127 — Add session color' '/color pink'
```

(`--remote-control` is there unless the repo turned off `agent_settings.claude.remote_control`; see `docs/settings.md`.)

The binary is the **resolved** `claude` path (`tools::resolve_tool`), not a bare `claude` left to PATH. The task runs in VS Code's integrated terminal, whose PATH is whatever that VS Code process inherited — and a VS Code launched by a packaged mAIestro Code at login can carry the minimal Launch Services PATH, with no `claude` on it. So the same `tool_paths.claude` override that pins mAIestro Code's own drafting calls also decides which binary the *session* starts with; when nothing concrete resolves, `resolve_tool` yields the bare name, leaving it to PATH. Existing worktrees pick the resolved path up on their next reopen, via the `refresh_vscode_files` regeneration described below.

**Codex sessions get no session color.** For a repo whose agentic coding CLI is Codex, the task runs the resolved `codex` binary alone — `'/opt/homebrew/bin/codex'`, labelled "Start Codex". Codex has no `--name` or `/color`, and any initial prompt would start a real model turn, so the session itself carries neither the name nor the color. Everything else still applies: the popover row and VS Code's title/status/activity bars are themed with the worktree's color exactly as for Claude, and `window.title`, the terminal font, and teardown's window matching don't depend on the agent. The session record stores the agent, so the regenerated task on reopen keeps launching the record's agent: the one the worktree was spawned with, unless the user switched it from the row's command strip (see *Switching a session's agentic coding CLI* below).

**Antigravity sessions get no session color either.** For a repo whose agentic coding CLI is Antigravity, the task runs the resolved `agy` binary alone, labelled "Start Antigravity". `agy` has no session-name flag and no `/color`, and an initial prompt (`-i`) would start a real model turn, so the same rules as Codex apply. The bars, popover row and window title are still themed. Its status hooks live in the worktree's `.agents/hooks.json`, not on the command line (`docs/session-status.md`).

**Copilot sessions get a name but no session color.** For a repo whose agentic coding CLI is GitHub Copilot CLI, the task runs the resolved `copilot` with the session title as its name, e.g. `'/opt/homebrew/bin/copilot' --name '⭐ #203 — GitHub Copilot CLI support'`, labelled "Start Copilot". Copilot has no `/color`, and an initial prompt (`-i`) would start a real model turn and spend a premium request, so none is sent. The task doesn't pass `--no-auto-update` either: updating the interactive CLI is the user's call. The bars, popover row and window title are still themed. Its status hooks live in the worktree's `.github/hooks/maiestro-status.json` (`docs/session-status.md`).

Not via a flag: Claude Code's `--agent-color` is only honored alongside `--agent-id`/`--agent-name`/`--team-name` (teammate sessions) and is **silently ignored** on its own. A leading-slash initial prompt is dispatched as a command, so this costs one line in the transcript and no model call.

On macOS the task is a `shell` task whose command single-quotes the binary and every value argument. On Windows it is a `process` task: the resolved binary as `command` plus a plain `args` array, run directly with no shell. The user's default terminal shell (PowerShell or cmd) therefore never parses it; PowerShell would read a quoted path followed by flags as an expression, not a command.

Because the launch command lives in the worktree's generated `.vscode/tasks.json`, a worktree keeps whatever its original spawn baked in. So the **reuse** spawn path regenerates the `.vscode` files (`spawn::refresh_vscode_files`), mirroring what `reconcile_session_hooks` does for hooks: reopening picks up changes to what we generate, so a worktree spawned by an older build is brought up to date on its next reopen. The values come from the **session record**, not the caller's freshly picked theme — reopening must never re-theme a worktree. It is best-effort: no session record means no rewrite, and a write failure only warns. Note this overwrites `.vscode/settings.json` and `tasks.json` on every reopen, so hand edits to those generated files do not survive.

## Switching a session's agentic coding CLI

**Agentic Coding CLI…** in a row's command strip opens a picker listing the available agentic coding CLIs (`AgentSwitchDialog`, current one marked, with a short explanation). Choosing another (`session_agent::session_set_agent`) changes an existing worktree's agentic coding CLI without re-spawning it. It updates the session record's `agent` and installs the new agent's status hooks (removing our Claude hooks from `.claude/settings.local.json` when leaving Claude, or our `maiestro-status` group from `.agents/hooks.json` when leaving Antigravity, and keeping the user's). It then regenerates the `.vscode` files from the record with `refresh_vscode_files`, so the switch never re-themes the worktree: the color, emoji, title, and branch stay the same. The old agent's conversation does not carry over.

The folder-open task only runs when VS Code opens the folder fresh (and a Terminal window runs only the command it was opened with). So if the session's window is open during a switch (`terminal_host::window_open`), the record also stores `editor_agent`, the agent that window is still running, and the row offers **Restart VS Code** (**Restart Terminal** for a Terminal session). `session_restart_editor` closes the window and confirms it is gone, reusing teardown's `terminal_host::close_and_wait` and blocking with the same Accessibility (VS Code) or Automation (Terminal) shortcut when it can't. (On Windows the window is found by its title with `EnumWindows` and closed with `WM_CLOSE`, which needs no permission, so the Accessibility case never arises there. Opening an already-open worktree raises its window with `SetForegroundWindow`; if Windows' foreground lock refuses that, the open falls through to `code <dir>`, which has VS Code raise the window itself.) It then clears the status record and reopens the folder. If the user picks **Later**, `session_open_in_editor` returns `restart_required` instead of focusing the old agent's window, for as long as that window stays open. Once it is closed, the next open launches the new agent and clears `editor_agent`. Switching back before restarting cancels the pending restart.

## Terminal.app sessions

A repo whose `terminal_host` is `terminal_app` (macOS; `docs/settings.md`) opens each session in **its own Terminal.app window** instead of VS Code. `terminal_host.rs` dispatches every open, focus, probe and close on the session record's `terminal_host`; `terminal_app.rs` drives Terminal. There is no tab or per-repo grouping: Terminal's AppleScript can open windows but not tabs (tabs would need System Events keystrokes and the Accessibility grant), so every session gets a window.

**Launch.** `terminal_app::launch` runs `osascript` with an **argument list**: the AppleScript is a constant that reads every value from `argv`, so the command line and title are never spliced into script source. It runs `do script` with `cd <worktree> && printf <OSC 0 title> && <session command>`, where the session command is exactly what VS Code's folder-open task runs (`terminal_host::session_argv` + `shell_command`, so the same resolved agent path, flags and `/color` prompt), every value single-quoted by `tools::shell_quote`. `do script` types that line into a new login shell, so the session gets the user's full ambient environment. When Terminal wasn't running, the session takes over the window Terminal opens at launch rather than leaving an empty one beside it. The script returns the new window's `id` and its tab's `tty`, stored on the session as `terminal_app_window`.

**Title and color.** The tab's `custom title` is `<repo>: <session title>` (e.g. `maiestro: 🍋 #243 — Terminal.app session host`), with `title displays custom title` on; the OSC 0 sets the same title from the shell. Terminal ignores OSC 11, so the tint is set through AppleScript instead: the tab's `background color` is `theming::dark_tint` of the worktree color (a near-black neutral, `#1c1c1c`, with 10% of the color mixed in — a subtle tint, so the hue names the worktree without competing with the session's own colors, and near-white text stays readable on all eight palette entries; a unit test checks each one stays dark and distinct), and its `normal text color` / `bold text color` are set to near-white, because a light profile's black text would be unreadable on it. AppleScript colors are 16-bit, so each 8-bit channel is scaled by 257.

**Terminal's profiles are never modified.** These are properties of the one tab we opened: Terminal keeps a per-tab copy of the profile's colors, and the named settings set (and `com.apple.Terminal.plist`'s `Window Settings`) stays untouched. We never create, edit or select a settings set, never change the default or startup profile, and write nothing to Terminal's preferences. On disk, a Terminal session writes only inside the worktree folder (its status hooks) and mAIestro Code's own `~/.maiestro/` records. No `.vscode/` files are generated for a Terminal session (`refresh_vscode_files` skips it): opening that folder in VS Code would otherwise start a second agent from the folder-open task.

**Focus and reopen.** A stored handle is trusted only while its window still holds a tab on the recorded `tty` (Terminal reuses window ids once it restarts). Reopening the worktree or clicking the row's Terminal button focuses that window (`set index … to 1`, un-minimized, `activate`); when it is gone (closed, or Terminal quit), a fresh window is opened and its handle recorded. A live window is never doubled: a second window would run a second agent in the same worktree. None of these scripts launches Terminal just to look — a Terminal that isn't running has no session window.

**Close (teardown and restart).** `terminal_app::close_and_wait` first probes the handle, then ends the session the way closing a terminal would: a `SIGHUP` to every process of **ours** on the tab's tty (listed with `ps -t` — `pkill -t` can't resolve `ttys…` names on current macOS — so Terminal's root-owned `login` is left alone). The signal goes out only after the probe has confirmed the tty still belongs to this window, so a reused tty never takes down someone else's shell. With nothing left running, `close window … saving no` closes without Terminal's "terminate running processes?" sheet; if something ignored the hangup, a `SIGKILL` follows after ~1.5 s (the user already confirmed the teardown). The window must be confirmed gone within ~4 s, as for VS Code.

**Automation permission.** The first Apple event to Terminal raises macOS's prompt "mAIestro Code wants to control Terminal". A denial fails every script with `-1743`, which becomes one actionable message naming System Settings → Privacy & Security → Automation → mAIestro Code → Terminal: on the work item when the spawn's launch fails (`status::write_spawn_error`), inline when a reopen fails, and as a Check Health failure (`docs/health-check.md`). Teardown and restart can't see the window without the grant, so they fall back, as VS Code does without Accessibility, to the permission-free `worktree_in_use` check, and the blocked prompt offers **Open Automation Options** (`open_automation_settings`) instead of the Accessibility shortcut. Each script is bounded by a 120 s timeout, long enough for the user to answer the prompt.

`terminal_app.rs` has an ignored end-to-end test that drives the real Terminal.app — launch, check the tab (not the profile) carries the tint, focus, close with a process still running, and compare the profiles before and after: `cargo test terminal -- --ignored`.

## cmux sessions

A repo whose `terminal_host` is `cmux` (macOS; `docs/settings.md`) opens each session as **a cmux workspace**: a vertical tab in a cmux window. `terminal_host.rs` dispatches on the session record as for the other hosts; `cmux.rs` drives cmux.

**Through cmux's own CLI.** Every call runs the `cmux` CLI bundled in cmux.app (`tools::find_tool("cmux")`, app bundle first — see `docs/tool-resolution.md`) with an **argument list**, never a shell string, and the current verbs (`workspace create` / `select` / `close`, `CMUX_QUIET` set so the legacy-alias notice never reaches stderr). The CLI talks to cmux over its socket. The caller-context variables cmux sets in its own terminals (`CMUX_WORKSPACE_ID`, `CMUX_SURFACE_ID`, `CMUX_TAB_ID`) are dropped from the child's environment, so a mAIestro Code started from a cmux terminal (in development) never targets its own workspace by accident.

**Socket access.** cmux admits an outside process like mAIestro Code only in its **Automation** or **Password** socket control mode (*cmux Settings → Automation → Socket Control Mode*). Both admit only processes running as the same Mac user. mAIestro Code handles **no password**: it never passes `--password` and never sets `CMUX_SOCKET_PASSWORD`; in password mode the CLI finds the password saved in cmux by itself, so it never appears in our arguments or logs. The default `cmuxOnly` refuses us; that, a missing password and a rejected password are each classified from the CLI's error (`CmuxError`) into an actionable message naming the setting, shown on the work item when a spawn fails and inline when a reopen does. We never fall back to `cmux <path>`, and never change cmux's settings, `~/.config/cmux/` or its password. Check Health reports the mode (`docs/health-check.md`).

**Launch.** `cmux::launch` first pings the socket; when cmux isn't running it starts it with `open -a cmux` and waits (up to ~20 s) for the socket. It then picks the window (below) and runs `cmux --json --id-format uuids workspace create --window <uuid> --name <title> --cwd <worktree> --command <cmd> --focus true`. The name is `<repo>: <session title>`, as for Terminal. `--command` is typed into the new terminal's login shell, so the session gets the user's full ambient environment; nothing is injected (no `--env`). The command is `session_argv` + `shell_command` with the **bare agent name** in place of the resolved path (below). The workspace is then colored with the worktree's palette color (`workspace-action --action set-color --color '#RRGGBB'`; a failure only warns) and brought forward. The session records the workspace's and window's **UUIDs** as `cmux_workspace` — never refs or indexes, which shift as windows open and close.

**cmux's agent integration runs.** In a cmux terminal, cmux puts per-surface shims on PATH (`~/.cmuxterm/cmux-cli-shims/…`). Its Claude shim (`cmux-claude-wrapper`) adds cmux's own hooks through `--settings` and a `--session-id`, then runs the real `claude`, which is what drives cmux's notifications, sidebar status and session tracking. Starting the agent by its bare name (`Agent::tool()`) lets that shim catch it, and cmux decides which binary runs (its *Automation → Claude Binary Path* setting, then the shell's PATH) — a deliberate exception to "a `tool_paths` pin is authoritative", which still governs mAIestro Code's own calls. Claude Code adds `--settings` hooks on top of the worktree's `.claude/settings.local.json`, so mAIestro Code's status hooks and quota statusline keep working; the wrapper sets no `statusLine`. We never call the wrapper directly or set any `CMUX_*` variable for it. Two things follow from leaving it to cmux: if the user's shell startup puts another `claude` ahead of the shim on PATH, cmux's integration doesn't run (the session still works); and with cmux's opt-in AI workspace naming on, cmux may rename our workspace.

**Window choice (`terminal_layout`).** The global `terminal_layout` (`docs/settings.md`) picks the window a new workspace joins. `per-repo` (the default) joins the window of another live cmux session of the same repo; `tabs` joins the window of any live cmux session; `windows` always opens a new one. The candidates come from the session records (`terminal_host::cmux_siblings`), each looked up afresh (`cmux::locate`), so a workspace the user dragged to another window is followed — there is no separate state file. When no candidate is live, `cmux new-window` opens one (it prints the window's UUID), and the empty workspace a new window comes with is closed once the session's is in. Changing the layout affects new sessions only.

**Focus and reopen.** `cmux::locate` asks `cmux --json --id-format uuids identify --workspace <uuid>`; its `caller` block names the workspace's current window, or is `null` when the workspace is gone. Reopening the worktree or clicking the row's cmux button raises that window (`focus-window`) and selects the workspace (`workspace select`), recording the window when it changed; when the workspace is gone (closed, or cmux quit), a new one is opened. A live workspace is never doubled. A lookup that fails for any other reason (no socket access) is an error, not "absent", since opening would start a second agent.

**Close (teardown and restart).** `cmux::close_and_wait` runs `workspace close --workspace <uuid> --force` and confirms the workspace is gone within ~4 s; `--force` because cmux otherwise refuses while a process (the agent) runs in it, and the user already confirmed the teardown. An already-gone workspace counts as closed. Without socket access we can neither look nor close; then, as for VS Code without Accessibility, `worktree_in_use` decides, and the blocked prompt names the cmux socket setting instead of a System Settings button (cmux's gate is not a macOS privacy grant, so `TerminalHost::permission()` is `None` for it).

**The repo row's open button** opens the cloned repo in cmux with `open -a cmux <dir>` — a plain workspace, no agent, nothing tracked, no socket access needed. No `.vscode/` files are generated for a cmux session, as for Terminal.

`cmux.rs` has an ignored end-to-end test against the real cmux (socket mode Automation or Password): launch, look up, focus, a second session joining the window under `per-repo`, and force-closing both with a process running: `cargo test cmux -- --ignored`.

## Windows Terminal sessions

A repo whose `terminal_host` is `windows_terminal` (Windows; `docs/settings.md`) opens each session as **a Windows Terminal tab**. `terminal_host.rs` dispatches on the session record as for the other hosts; `windows_terminal.rs` drives Windows Terminal.

**Launch.** `windows_terminal::launch` runs `wt -w <window> new-tab -d <worktree> --title <title> --suppressApplicationTitle --tabColor <#RRGGBB> -- <agent> <args…>` with an **argument list**, through `tools::tokio_command("wt")` (bounded by a timeout, `kill_on_drop`). The tab runs `session_argv` directly — the **resolved** agent path and the same flags and Claude `/color` prompt as VS Code's folder-open task — with no shell in between, so `tool_paths` pins apply unchanged. The tab inherits mAIestro Code's own environment (its recovered login PATH), whether it opens a new window or joins an existing one, as a VS Code session started through the `code` CLI does; nothing is injected. `wt` returns at once, before the tab exists, so the launch then waits (up to ~10 s, for a cold start) until a tab with that title appears; if none does, the spawn fails with an actionable error and nothing is recorded. A tab of the same title that is already open fails the launch too, since two tabs of one title couldn't be told apart.

**Argument encoding.** `wt` rebuilds the child's command line itself, lossily: it wraps an argument that contains a space in `"…"` but escapes nothing inside it (no embedded `"`, no trailing `\`), drops empty arguments, doesn't wrap one that contains a tab, splits its whole command line on `;` (its subcommand separator), and expands `%VAR%`. `wt_args` pre-encodes each agent argument to survive that (`encode_arg`): the content escaped by the MSVC rules with the outer quotes left to `wt`, `""` for an empty argument, and `;` as `\;` (also in `-d` and `--title`). `%` has no escape: in user-derived text — the tab title and the session's `--name` — it becomes the fullwidth `％`, and control characters (tab, newline) a space (`windows_terminal::user_text`, applied to the session title before the command is built); a `%` anywhere else (the agent path, the worktree, a Codex `-c hooks.…` override) fails the launch loudly rather than being expanded. Unit tests round-trip the encoding through a model of `wt`'s rebuild and MSVC parsing.

**Title and color.** The tab title is `<repo>: <session title>`, as for Terminal and cmux, and `--suppressApplicationTitle` keeps the agent's own OSC 0 title from replacing it. The worktree's palette color is the **tab color** (`--tabColor`). There is no background tint: that would need a shell prelude (OSC 11) between `wt` and the agent, or a shipped color-scheme fragment.

**Window choice (`terminal_layout`).** The global `terminal_layout` (`docs/settings.md`) names the `wt` window a new tab goes into: `maiestro-<ws-id>` for `windows` (a window per session), `maiestro-<owner>-<name>` for `per-repo` (the default), and `maiestro` for `tabs` (one shared window). `wt -w <name>` reuses the window of that name, or opens one when it is gone, so — unlike cmux — no window state is looked up or kept. Changing the layout affects new sessions only.

**The title is the tab's identity.** `wt` has no tab ids, and tab indexes and window ids shift, so the session records the title it launched with (`windows_terminal_tab`), never an index. Tabs are found through **UI Automation**: each is a `TabItem` named after its title, in a `CASCADIA_HOSTING_WINDOW_CLASS` window, looked up across **every** Windows Terminal window so a tab dragged to another window is followed. Same-user windows need no grant or elevation, so `TerminalHost::permission()` is `None`. Every UIA call runs on a blocking thread with COM initialized there. Looking never calls `wt`: `wt -w <name>` on a closed window would open a new, empty one.

**Focus and reopen.** Reopening the worktree or clicking the row's Windows Terminal button selects the session's tab (`SelectionItemPattern`), restores its window if minimized and brings it forward; when the tab is gone, a new one is opened and recorded. A live tab is never doubled, and a lookup that fails is an error, not "absent", since opening would start a second agent.

**Close (teardown and restart).** `windows_terminal::close_and_wait` invokes the tab's own close button (the `CloseButton` inside its `TabItem`), which closes it with the agent still running and asks nothing, then confirms within ~4 s that the tab is gone. Ending the agent's process isn't enough: with the default `closeOnExit`, Windows Terminal keeps a tab open when its process exits non-zero. A UIA failure is `StillOpen`, never `Closed`, because Windows refuses to remove a worktree that a process still runs in and `worktree_in_use` can't tell on Windows; a session switch likewise treats a failed lookup as an open tab. Closing a tab brings its Windows Terminal window forward, which would blur — and so hide — the popover a teardown was started from; while a close is in flight the popover doesn't auto-hide (`windows_terminal::focus_held`), and once the tab is gone the foreground is handed back to the window that had it, but only if a Windows Terminal window took it.

**The repo row's open button** opens the cloned repo as a **tab**, never a window of its own while one is open: `wt -w <window> new-tab -d <cloned repo>`, where the window is the one the repo's sessions share under `terminal_layout` (`maiestro-<owner>-<name>` for `per-repo`, `maiestro` for `tabs`) and, under `windows`, where no window is the repo's, the most recently used Windows Terminal window (`-w 0`) (`windows_terminal::folder_window_name`). It is a plain tab with the default profile — no agent, nothing tracked. No `.vscode/` files are generated for a Windows Terminal session, as for Terminal.

**Windows Terminal's settings are never modified.** Its `settings.json`, `state.json`, profiles and color schemes are untouched, and no settings fragment is written: the title and tab color are arguments of the one `new-tab` we run.

**Caveats.** A tab the user renames is no longer found, so reopening starts a fresh tab — a second agent — beside it. With `firstWindowPreference: persistedWindowLayout`, Windows Terminal's own session restore may relaunch an agent tab after a restart; mAIestro Code doesn't fight it. An npm `.cmd` agent shim re-parses arguments that contain `"` (Codex's hook overrides) through `cmd`, the same limit VS Code's `process` task has.

`windows_terminal.rs` has an ignored end-to-end test against the real Windows Terminal: launch a tab with a hostile title (`"`, `;`, `%`) and arguments, checked by a child that writes what it received, focus it, close it with the child still running, check `settings.json` is byte-identical, and read the version without starting `wt`: `cargo test windows_terminal -- --ignored`.
