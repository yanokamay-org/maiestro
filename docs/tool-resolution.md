# External tool resolution

mAIestro Code shells out to a handful of external CLIs *itself* (distinct from the user-facing session it launches, which inherits the full ambient env). When the app is launched from the packaged bundle (`/Applications/mAIestro Code.app/…`) at login, macOS Launch Services gives it a **minimal `$PATH`** (`/usr/bin:/bin:/usr/sbin:/sbin`) with no shell profile sourced, so a bare `Command::new("claude")` (or `git`, or `code`) can fail to resolve or pick the wrong binary (e.g. the `/usr/bin/git` Xcode stub instead of a Homebrew git). `backend/src/tools.rs` centralizes resolution.

- **Tools that go through `tools`:** the agentic coding CLIs `claude`, `codex`, `agy` (Antigravity) and `copilot` (GitHub Copilot; AI drafting in `drafting::agent_text`, the Check Health probe, *and* the agent path baked into a worktree's generated VS Code startup task by `editor::write_vscode_files`), `git` (`gitops::git()` / `gitops::local_branch_exists()` — worktree add, branch checks), the VS Code `code` CLI (`editor::open_vscode`), and the `cmux` CLI (`cmux.rs`, for repos whose terminal host is cmux), and Windows Terminal's `wt` (`windows_terminal.rs`, for repos whose terminal host is Windows Terminal). These are the ones invoked directly with the minimal PATH.
- **Tools that don't:** `open`, `osascript`, `lsof` are system binaries under `/usr/bin`, always on the minimal PATH; the login shell used for `post_spawn_commands` is invoked with `-l` so its children get a full PATH (on Windows it is `%ComSpec% /C`, given the process PATH and no console window); and `gh` is **not used at all** (GitHub is the REST API — see "Talk to GitHub directly" in `CLAUDE.md`).
- **Login-shell PATH, recovered once.** At startup `tools::init()` (called from `setup()`) runs `$SHELL -l -c 'echo $PATH'` and caches the result — the user's *real* PATH (Homebrew, asdf/nvm shims, …). `enriched_path()` = that PATH followed by the process's own PATH (dedup, order-preserving), and every directly-spawned child is given it (`tools::command` / `tools::tokio_command`) so sub-tools the resolved binary calls resolve too. This one layer fixes every tool — and any added later — with no config.
- **`resolve_tool(name)` precedence:** an explicit override (`tool_paths` in global settings) is **authoritative** — once set it is the *only* source, so a pinned path can never silently resolve to a *different* binary. `resolve_tool` invokes it **verbatim** (even if missing, so a broken pin fails loudly with `No such file` rather than running a PATH binary); `find_tool` returns `Some` only when the pin exists, else `None` (a hard "not found" — **no** fall-through to auto-resolution). Only when **no** override is set do we auto-resolve: `which` on the enriched PATH → known install locations (`~/.claude/local/claude`, `~/.local/bin` — where `pip install --user` and the native installers put `claude` and `codex`, and Antigravity's install script puts `agy`, `/opt/homebrew/bin` (also the `antigravity-cli` cask's `agy`), `/usr/local/bin`, …) → (for `resolve_tool`) the bare name as a last resort. `stale_override(name)` returns the configured pin when it's set but missing (exactly the case `find_tool` returns `None` despite a pin), so the health check can name it. `resolved_status` reports the picked path + whether it exists, for the Settings UI. `tools_resolved` is the Tauri command backing the "Tool paths" status line.
- **Windows.** PATH entries are split and joined with the platform's own separator (`std::env::split_paths` / `join_paths`), since a `:` split would cut `C:\…` apart. There is no login-shell probe: a Windows GUI app already inherits the user and machine PATH from the registry, so `enriched_path()` is just the process PATH. A name without an extension resolves only to `name` plus one of `%PATHEXT%`'s extensions, in that order (`claude` → `claude.exe`, `code` → `code.cmd`); the extensionless `code` shell script VS Code ships for WSL is never picked. The same applies to the known install locations, so `~/.local/bin/claude` finds the native installer's `claude.exe`. The other macOS locations simply don't exist there. `codex` and `agy` also probe their Windows installers' folders, `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe` and `%LOCALAPPDATA%\agy\bin\agy.exe`. Those installers only append the folder to the user `Path`, which a process started before the install doesn't see, so these probes find a CLI installed while mAIestro Code was running. For `code`, the Windows known locations are the CLI inside VS Code's two default installs, `%LOCALAPPDATA%\Programs\Microsoft VS Code\bin\code.cmd` (per-user installer) and `%ProgramFiles%\Microsoft VS Code\bin\code.cmd` (system installer) — the counterpart of the macOS app-bundle entry, for an install whose "Add to PATH" option was unticked. There is no `open -a` fallback on Windows, so `open_vscode` errors when `code` can't be found. A release build is a GUI-subsystem app, so a console child it starts would get a console window of its own flashing up; `tools::command` / `tools::tokio_command` therefore spawn every directly-invoked tool with `CREATE_NO_WINDOW` (`tools::hide_console`, a no-op elsewhere). `tauri dev` never shows the flash, since the debug build has its own console.
- **Override config** lives in `~/.maiestro/settings.json`'s `tool_paths` (see `docs/settings.md`): a per-tool absolute path, empty = auto-resolve.

**An agentic coding CLI binary is resolved only when that agentic coding CLI is used.** `claude` is no longer assumed: a repo's AI calls, its spawned session's startup task, and its Check Health probe resolve the binary of the repo's effective agentic coding CLI (`repo_settings::effective_agent`, or the session record's `agent` for the startup task) and nothing else. On a machine with only `codex` installed, a Codex repo never invokes `claude` or `agy`, and the same holds for each agentic coding CLI. Every agentic coding CLI is still listed in `tools_resolved`, so the General panel's "Tool paths" block shows `claude`, `codex`, `agy` and `copilot`, and any can be pinned.

**cmux: the app bundle first.** cmux installs no CLI on PATH; its CLI lives at `cmux.app/Contents/Resources/bin/cmux`. Without a pin, `find_tool("cmux")` probes `/Applications/cmux.app/…` and `~/Applications/cmux.app/…` **before** the PATH, because a `cmux` on PATH may be an unrelated tool of the same name.

**Windows Terminal: its app execution alias.** Without a pin, `find_tool("wt")` looks on PATH, then at `%LOCALAPPDATA%\Microsoft\WindowsApps\wt.exe`, the app execution alias Windows Terminal installs. The alias is a reparse point, but `Path::is_file()` is true for it and `std::process::Command` spawns it, so it needs no special case. `wt` is resolved only when a repo actually uses Windows Terminal. A Windows Terminal tab runs the resolved agent path directly, so a `tool_paths` pin decides the session's binary there as everywhere else.

**Tool paths lists a terminal host's tool only on its own OS.** `tools_resolved` (what the General panel's Tool paths rows come from) reports `cmux` only on macOS and `wt` only on Windows (`tools::listed_here`, from each host's `supported_here()`); the agents, `git` and `code` are listed everywhere.

**A cmux session starts the bare agent name, not the resolved path.** Everywhere else the session's launch command bakes in the resolved agent binary, so a `tool_paths` pin decides which binary the session runs. A cmux session is the deliberate exception: its `--command` starts `claude` (or `codex`, `agy`, `copilot`) by name, so cmux's per-surface shims on the terminal's PATH catch it — cmux's Claude wrapper adds cmux's own hooks for its notifications and sidebar status — and cmux decides the binary (its *Automation → Claude Binary Path* setting, then the shell's PATH). The pin still governs mAIestro Code's own calls (drafting, Check Health). See "cmux sessions" in `docs/theming.md`.

**Antigravity's binary isn't its setting value.** The `agent` value is `antigravity`, but the CLI (and its `tool_paths` key) is `agy`. Always resolve an agent through `Agent::tool()`, never `Agent::as_str()`.

**Copilot: never the VS Code shim.** VS Code's Copilot Chat extension puts a `copilot` shell script on PATH at `~/Library/Application Support/Code/User/globalStorage/github.copilot-chat/copilotCli/copilot`. With the real CLI installed it passes calls through; without it, it asks *"Install GitHub Copilot CLI? [y/N]"* and waits, which would hang a headless call. Auto-resolution therefore skips any candidate whose path contains `github.copilot-chat/copilotCli/` (`tools::is_copilot_shim`) and keeps looking, so with only the shim installed `copilot` counts as **not found** and Check Health names the shim (`tools::copilot_shim_on_path`). Drafting refuses to run when `find_tool("copilot")` is `None`. A `tool_paths.copilot` pin stays authoritative even if it points at the shim. Known install locations: `/opt/homebrew/bin/copilot` (`brew install copilot-cli`, and `npm install -g @github/copilot` when npm's prefix is Homebrew), `/usr/local/bin/copilot`, `~/.local/bin/copilot` (the `gh.io/copilot-install` script) and `~/.npm-global/bin/copilot`.

**An npm install of Copilot needs `node`.** Its `copilot` entry point is a Node script (`#!/usr/bin/env node`) that runs the platform's native binary. Child processes get the enriched login-shell PATH, which has `node` for anyone who installed through npm; if it doesn't, Check Health reports `node` missing.
